# 通用 LLM 配置与确认组合商品摘要

## Goal

将订单识别使用的模型端点提升为全局 LLM 配置，并为每个已确认的发票-订单组合异步生成持久化商品摘要。摘要作为组合的 `displayName`，供匹配页、项目详情和项目导出统一使用；模型不可用时不得阻止匹配或导出。

## Requirements

- Ollama/OpenAI 兼容提供商、地址、模型与密钥归入全局 LLM 配置；订单识别只保留自己的并发参数，视觉识别与文本摘要共用当前模型。
- `settings.toml` 升级时完整保留旧提供商、端点、模型、密钥和订单并发；公共设置响应不得泄露凭据。
- 确认单个或批量匹配时，在原事务内创建 `pending` 摘要状态，提交后由独立单并发队列异步生成；外部请求不进入匹配事务。
- 应用启动自动补齐历史确认组合，并把中断的 `processing` 恢复为 `pending`；单次失败保留错误并等待人工重试，不无限自动重试。
- 摘要输入包含发票销售方、全部发票详细条目，以及每张确认订单的店铺名称和全部商品条目。
- 摘要只概括实际商品，合并同类商品并覆盖主要类别；不要求体现用途，也不得主动推断购买目的、报销场景或使用者。
- 摘要为中文单行纯文本，通常 10-30 个字符，简单商品允许更短；不得包含商家、金额、单号、数量清单或生成过程说明。空值或超过 60 个 Unicode 字符视为失败。
- 商品、店铺、发票销售方或发票条目变化且匹配仍存在时自动重新排队；会解除匹配的编辑继续删除整个关系。输入哈希必须防止过期请求覆盖新输入。
- 更换模型只影响新任务、数据变化和人工重试，不批量重写已成功摘要。
- 摘要成功时作为组合 `displayName`；待处理、处理中或失败时确定性回退为全部订单商品名，再回退到订单号/内部 ID。
- 匹配页和项目详情显示摘要及状态；失败项可重试。项目页面对未完成/失败摘要给出非阻塞 info 提示。
- 项目 XLSX 增加“订单摘要”列并保留订单号列；ZIP 组合目录使用安全化后的 `displayName`。摘要异常不影响导出资格，也不在导出时同步调用 LLM。
- 发布独立 `match-summary-updated` 失效事件，让匹配页和项目页重新读取权威数据。
- 更新项目级 `AGENTS.md` 与相关 Trellis 合同，记录通用 LLM、摘要队列、降级和导出命名约束。

## Technical Approach

- 将现有 OCR 客户端抽象为通用 LLM 客户端，保留两种协议实现并增加结构化文本摘要方法。
- 扩展 `invoice_matches` 保存 `display_name`、状态、错误、提供商、模型、输入哈希和生成时间；确认关系删除时依靠级联生命周期清理。
- 新建进程内唤醒器驱动 SQLite 持久任务状态；每次处理重新读取当前私有 LLM 设置和当前组合输入。
- 对模型调用前后的输入哈希做条件持久化，保证编辑、重试和撤销确认期间的并发正确性。
- 由后端统一计算对外 `displayName`，避免前端和导出各自拼接产生差异。

## Decision (ADR-lite)

**Context**: LLM 调用慢且可能离线，而匹配确认和批量原子性是核心业务约束。

**Decision**: 匹配先持久化、摘要后异步生成；使用一个全局模型配置和独立单并发摘要队列；摘要只描述商品，不默认推断用途；失败采用可见但非阻塞的降级名称。

**Consequences**: 确认后短时间内可能显示降级名称；需要状态、事件、恢复和重试机制，但模型故障不会阻断核心流程。

## Out of Scope

- 不支持按用途配置多个 LLM 或分别选择视觉/摘要模型。
- 不允许人工编辑摘要，也不提供模型切换后的全量批量刷新。
- 不改变匹配金额、日期、店铺规则及项目导出完整性条件。
- 不把组合摘要写入单条订单记录。

## Technical Notes

- 相关合同：后端数据库、订单导入、订单发票匹配、项目导出；前端应用、匹配与项目工作区合同。
- 当前项目已有 `invoice_matches` 和 `invoice_match_orders` 持久关系，现有 `productSummary` 只是订单列表展示拼接，不是本功能的组合摘要。
